Guía Resumida de Diagramas UML — Metodología de Sistemas II

Objetivo: Material de estudio conciso sobre los 6 diagramas UML trabajados en las guías y carpetas técnicas de la materia (enfoque de Craig Larman y Dossier UTN-FRT). Cada diagrama incluye para qué sirve, un único ejemplo aplicado al mismo caso (Reserva de Turno de Cancha — Club Deportivo Cerro Alto), el detalle de cada ítem del gráfico y el detalle de cada línea o flecha.

1. Diagrama de Casos de Uso

  • Etapa: Análisis de requisitos (¿Qué debe hacer el sistema?).

  • Para qué sirve: Muestra el panorama general de quién interactúa con el sistema desde afuera (actores) y qué funcionalidades ofrece el sistema hacia ellos (casos de uso). Funciona como un índice visual de las historias escritas de casos de uso.

Regla de oro de examen: El caso de uso real es el texto (historia), no el dibujo. En el diagrama: «include» sale del base (obligatorio); «extend» apunta hacia el base (opcional).

2. Modelo de Dominio (Clases de Análisis)

  • Etapa: Análisis Orientado a Objetos puro (¿Qué cosas existen en el mundo real del negocio?).

  • Para qué sirve: Representa visualmente los conceptos del mundo real (clases conceptuales), sus datos esenciales (atributos) y cómo se vinculan entre sí (asociaciones), sin pensar todavía en código ni en base de datos.

Regla de oro de Craig Larman: Un Modelo de Dominio JAMÁS lleva métodos/funciones, ni modificadores (+/-), ni claves foráneas (idCancha), ni artefactos de software (Controlador, BaseDeDatos, Pantalla).

3. Diagrama de Clases de Diseño (DCD)

  • Etapa: Diseño Orientado a Objetos (¿Cómo vamos a estructurar las clases en el código?).

  • Para qué sirve: Define el plano técnico de las clases reales de software: sus atributos tipados, visibilidad, métodos, interfaces, herencia y dependencias, aplicando principios SOLID y patrones de diseño.

4. Diagrama de Secuencia del Sistema (DSS)

  • Etapa: Análisis (¿Qué eventos cruzan la frontera entre el usuario y el software?).

  • Para qué sirve: Representa en orden cronológico (de arriba hacia abajo) qué estímulos envía el actor al software y qué respuestas devuelve el sistema para un escenario concreto de un caso de uso, tratando al software entero como una caja negra (:Sistema).

Regla de oro de Craig Larman: En un DSS nunca aparecen controladores, servicios ni tablas; solo el actor que toca el software y :Sistema. Además, los nombres de eventos deben empezar con verbo y no mencionar botones ni dispositivos físicos.

5. Diagrama de Secuencia de Diseño (DSD)

  • Etapa: Diseño Orientado a Objetos (¿Cómo colaboran internamente los objetos de software para resolver el caso de uso?).

  • Para qué sirve: Abre la caja negra del DSS y muestra, paso a paso en orden cronológico, las llamadas reales a métodos entre pantallas, controladores, servicios, repositorios y entidades para cumplir una operación.

6. Diagrama de Actividades

  • Etapa: Análisis de procesos de negocio y diseño de flujos/algoritmos (¿Cuál es el paso a paso del proceso, quién hace cada paso y qué decisiones o tareas en paralelo existen?).

  • Para qué sirve: Modela el flujo de trabajo (workflow) de un proceso completo de principio a fin, mostrando la secuencia de acciones, bifurcaciones condicionales, tareas simultáneas y el reparto de responsabilidades entre áreas o roles.
